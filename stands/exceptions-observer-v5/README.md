# exception-observer-probe v5 — только исходники

12.10.2026. Новый закрытый блок частей 1–3: **4 640 запусков, 232 дочерние группы**. Старые v4 raw не включены и не заменены. Windows-ответов в архиве нет.

## Быстрый запуск на настоящей Windows x64

Требуются официальный **llvm-mingw 20260505 UCRT, clang 22.1.5**, x64 PowerShell 7+, Python 3.10+. Сценарий ничего не скачивает и не устанавливает. Распакуйте пакет, прочитайте исходники, затем:

```powershell
pwsh -File .\run_windows.ps1 -Clang C:\tools\llvm-mingw-20260505-ucrt-x86_64\bin\x86_64-w64-mingw32-clang.exe -Python python.exe -OutputDirectory C:\results\v5-windows-2022-intel
```

На второй машине используйте новый каталог, например `v5-windows-2025-amd`. Не запускайте под подключённым отладчиком: проба сама не подключает и не отключает его. Системная конфигурация при этом остаётся частью измерения.

Сценарий проверяет native x64 Windows/PowerShell, target, версию clang; записывает SHA-256 компилятора и сведения окружения. Сам номер clang не доказывает происхождение дистрибутива — официальный архив 20260505 должен предоставить пользователь. Команда сборки:

```text
x86_64-w64-mingw32-clang -std=c11 -fms-extensions -O1 -g -Wall -Wextra -Werror -municode exception_probe.c -o exception_probe.exe
```

При неподдержанной архитектуре или отказе компиляции (включая настоящий рамочный SEH) сценарий останавливается и сохраняет blocker. Он не меняет класс пробы, не заменяет SEH на VEH и не повторяет работу с альтернативными флагами.

## Отдельный запуск той же вашей сборки

Для запуска уже самостоятельно собранного PE в вашей совместимой среде:

```text
exception_probe.exe --output NEW_RESULTS_DIRECTORY
python check_results.py NEW_RESULTS_DIRECTORY/raw.jsonl --summary NEW_RESULTS_DIRECTORY/summary.json
```

Windows-runner специально требует настоящую Windows x64; для переведённой среды используется прямой запуск, а описание окружения/ключа переводчика надо сохранить отдельно. Из архива поставки никакие готовые EXE не запускаются, потому что их в нём нет. В среде подготовки этой поставки PE не исполнялся ни нативно, ни через Wine.

Для двух рук переводчика используйте разные новые каталоги. Сохраните точные revision/build IDs, командную строку и состояние ключа; не смешивайте raw разных запусков. Сверка чисел возможна только после реального прогона.

## Что будет записано

- `raw.jsonl`: manifest, run_start, callback-наблюдения, run_result и lifecycle каждой группы
- `group-000.jsonl` … `group-231.jsonl`: первичные файлы изолированных групп
- `run_environment.json`, `input-and-binary-sha256.json`, журналы compiler/runner/probe/checker, runner.status.json
- `summary.json`: отчёт checker с явными списками пропущенных ключей и отдельным учётом unsupported/aborted

Одна группа живёт 20 повторов; дополнительная глубина стека меняется 0…19. Новый процесс не создаётся перед каждым повтором. Raw-файлы создаются исключительно через CREATE_NEW; существующие результаты не перезаписываются.

После сбоя/тайм-аута родитель сохраняет неизвестность. `runtime_aborted` не равен `exception_delivered=false`. `requested_policy_unsupported` не равен успешному продолжению. Полностью учтённая матрица тоже может быть не полностью измерена. В отчёте checker диагностические отклонения по структуре отделены от наблюдаемых различий; нет заранее заданного Windows oracle.

## Состав и чтение

1. `DESIGN.md`: закрытая матрица, ABI, first-PUSHFQ, TF, VCH, безопасности продолжения.
2. `MAPPING.md`: какие поля сопоставлять и что пока является только прогнозом.
3. `exception_probe.c`: C11 collector, observers, фиксированные клетки, parent/child runner.
4. `asm_fragment.h`: собственные статические asm-функции и корректные `.seh` записи; подключается один раз.
5. `generate_asm.py`: детерминированный генератор именно включённого asm-фрагмента; для обычной сборки запускать его не требуется.
6. `run_windows.ps1`, `check_results.py`, `test_checker.py`.
7. `check_static.py`: необязательный статический аудит **собственного** собранного PE; не запускает его.
8. `VALIDATION.md`, `SHA256SUMS`.

Главное изменение v5: девять однобайтных PUSHFQ. Любой разрешённый entry0…8 сохраняет флаги первой исполняемой командой. Первый образ читается из entry_rsp−8; последний образ хранится отдельно. Все GPR сохраняются до scratch-вычислений; RSP на входе реконструируется из точного числа PUSH. RF/VM в PUSHFQ image не сохраняются по архитектурному контракту.

API-параметры не разыменовываются. Собственные известные строки/объекты получают symbol+offset; системный код получает location без offset. Void API не имеют return_value. CheckRemoteDebuggerPresent использует только текущий процесс и раздельно пишет успех вызова, out BOOL и failure-only GetLastError.

## Локальные проверки без запуска PE

```text
python -m unittest -v test_checker.py
python -O -m unittest -v test_checker.py
python check_static.py PATH_TO_YOUR_OWN_PROBE.exe --tool-dir PATH_TO_LLVM_MINGW_BIN
```

`check_static.py` читает только собственный PE через llvm-objdump/readobj/nm: точные INT2D/CC и PUSHFQ bytes, порядок MOV-снимка, одинаковый alternate prologue/unwind, наличие рамочного SEH и рекурсивного depth-control. Это не проверка поведения Windows.

## Границы результата

Документация задаёт API signatures, смысл BOOL/out BOOL и архитектурные свойства PUSHFQ. Она не предоставляет готовой таблицы Windows по всем 12 RAX и всем обработчикам. Обзор Wine/FEX поставляется отдельным файлом/архивом; исходники другой реализации дают прогноз, не Windows raw.

Часть 5 ждёт ваши исходные v4 raw с Windows 2022/2025. Сообщённая вами прежняя таблица 21 клетки сохранена как контекст в MAPPING; сверка по полям здесь не выдумана.
