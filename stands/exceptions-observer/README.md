# Exception observer probe: Windows x64

Эталонная программа на C11 для ответа на вопрос: **какой `EXCEPTION_RECORD` и `CONTEXT` видит собственный обработчик программы и откуда возобновляется её собственный код?**

Пакет содержит исходники, сценарий PowerShell, проверяющий сценарий Python и описание. Готовый EXE и выдуманные результаты Windows не поставляются. Измерения нужно получить нативно на настоящей Windows x86-64, отдельно на `windows-2022` и `windows-2025`.

## Границы

- Только собственный код, собственные потоки и дочерние экземпляры этой же программы.
- Закрытый список из 12 исходных клеток; семь вариантов RAX для INT 2D дают **18 вариантов**.
- 3 раздельных наблюдателя × 2 предыстории арифметических флагов × 2 политики продолжения × 20 повторов = **4320 запусков клеток**.
- 216 дочерних процессов матрицы: один процесс на сочетание варианта, наблюдателя, флагов и политики. Внутри него все 20 повторов используют один процесс с глубиной вызовов 0…19. Малый блок контекстов выполняется ещё в одном собственном дочернем процессе, итого 217.
- Нет чужих процессов, поиска адресных диапазонов, перебора опкодов/прерываний, подключения к отладчикам, драйверов, ядра, исходников или тестов Wine.

## Требования

1. Нативная Windows x64. ARM64, эмуляция x64 на ARM64, x86 и WOW64 исключены из эталонного запуска.
2. PowerShell **7 или новее** (`pwsh`).
3. Уже установленный **llvm-mingw clang с целью x86_64-w64-windows-gnu** и соответствующими заголовками/библиотеками Windows. Сценарий ничего не скачивает и не устанавливает.
4. Python 3.10 или новее с доступной стандартной библиотекой. Сторонних Python-пакетов нет.
5. Запуск без подключённого отладчика. Эталон Windows получают без Wine; позднейший сравнительный запуск той же программы в своей реализации пользователь выполняет отдельно.

`-Clang` принимает путь к уже установленному исполняемому файлу компилятора либо имя приложения в PATH. По умолчанию используется `x86_64-w64-mingw32-clang`. Обычный MSVC-target `clang.exe` не эквивалентен llvm-mingw.

## Запуск

Из каталога исходников, в PowerShell 7:

```powershell
./run_windows.ps1 -Clang 'C:\tools\llvm-mingw\bin\x86_64-w64-mingw32-clang.exe' -OutputDirectory '.\results-windows-2022'
```

На другом образе используйте другой свежий каталог, например `results-windows-2025`. Если компилятор уже в PATH:

```powershell
./run_windows.ps1 -OutputDirectory '.\results-windows-2025'
```

Можно указать `-Python 'C:\path\to\python.exe'`. Каталог результата должен отсутствовать либо быть пустым: сценарий не смешивает новый прогон со старыми файлами. Проверка целевой архитектуры и сборка выполняются однократно. Ошибка сборки сохраняется как блокер; автоматического подбора компилятора, повторной сборки с другими флагами или замены SEH нет.

Публичный интерфейс скомпилированной программы:

```text
exception_probe.exe --output <каталог>
```

Внутренние аргументы дочернего режима не являются пользовательским интерфейсом. Программа сама создаёт фиксированные 216 групп и отдельный процесс малого блока. Каждый ребёнок создаётся приостановленным, включается в собственный kill-on-close job и только затем запускается. Основное ожидание ограничено 30 секундами; при необходимости завершается **только непосредственно созданный ребёнок**, после чего действует дополнительное ожидание завершения до 5 секунд. 216 × 30 секунд дают 108 минут одних основных ожиданий; cleanup и малый блок добавляют время. Нормальную длительность Windows здесь не предсказываем.

## Результаты

- `raw.jsonl`: объединённые исходные записи, включая отдельную запись на каждую доставку исключения и отдельный итог каждого повтора.
- `summary.json`: отчёт проверяющего сценария; отсутствующие клетки, дубликаты, нарушения схемы, неподдержанные случаи и изменчивость полей.
- `group-000.jsonl`…`group-215.jsonl` и `thread-context.jsonl` сохраняют доступные данные, если дочерний процесс не завершился штатно.
- `build/` и журналы сценария: компилятор, цель сборки, stdout/stderr, сведения об архитектуре и коды завершения.

Самостоятельная повторная проверка уже полученного файла:

```powershell
python ./check_results.py ./results-windows-2022/raw.jsonl --summary ./results-windows-2022/summary.json
```

Сценарий вызывает checker и после ненулевого кода завершения программы, чтобы частичный результат не остался без отчёта. Если сборка не получилась, запуска EXE и искусственного заполнения `raw.jsonl` нет. Ненулевой итог сценария требует чтения журнала и `summary.json`, а не игнорирования ошибки.

## Явные ограничения и неполные измерения

**У API нет доступной здесь документированной длины trap-инструкции.** Для `DebugBreak()` и обоих `RaiseException()` значение `instruction_length` отсутствует. Запрошенная политика прибавления длины не выдаётся за выполненную: она помечается неподдержанной, с явно записанной фактической попыткой оставить RIP. Сценарий не декодирует инструкции DLL и не перескакивает через них. Повторное исключение ограничено защитой собственного дочернего процесса.

**Для `CD 03` возможен RIP во втором байте команды.** Если наблюдатель получил `site + 1`, буквальное «оставить RIP» направляет исполнение внутрь `CD 03`. Этот переход помечается неподдержанным и заменяется только отдельным, явно отмеченным аварийным выходом из собственной пробы. Он не считается измеренным успешным продолжением. Аналогично отклоняются другие цели внутри многобайтной инструкции и вне разрешённых границ собственного кода.

**Безопасный выход не равен политике продолжения.** В `advance` прибавляется длина к *полученному* `Context.Rip`, а не устанавливается удобная метка после команды. В `keep_then_advance` первые три доставки оставляют RIP, четвёртая прибавляет длину; пятая доставка вызывает отдельную жёсткую защиту. Неприменимая цель или защита отражаются в raw/summary, а не скрываются как успешное выполнение.

**Снимок внутри API не обязан совпадать со входом в API.** Volatile GPR, XMM0…XMM5 и арифметические флаги могут измениться из-за вызова. Даже nonvolatile-регистры могут временно использоваться внутри DLL после сохранения: обязанность восстановить их относится к возврату из вызова, не к произвольной внутренней trap-точке. Все такие расхождения остаются наблюдениями; checker не объявляет их дефектом Windows.

**Контекст обработчика принадлежит ОС.** Перед чтением его не заполняют узором. Копируется только фиксированная публичная структура `CONTEXT`. Бит `0x40` сохраняется отдельно; общая длина заимствованной XSTATE-области недоступна из используемого документированного контракта и записывается как `null` с причиной. Смещения `CONTEXT_EX` не угадываются.

**Текущий поток — отрицательный контроль API.** Успешный `GetThreadContext(GetCurrentThread(), …)` не даёт валидного контекста текущего потока по документации Microsoft. Это прямо отмечено. `Dr4` и `Dr5` отсутствуют в публичном x64 `CONTEXT` и представлены как `null`, не как нули.

Отсутствие доставки обработчику — самостоятельный наблюдаемый исход, если собственная проба штатно дошла до цепочки. Авария/тайм-аут до результата не позволяет делать такой вывод.

Полная учётная матрица, в которой каждый ключ объяснён, **не равна** полностью измеренной матрице. Неподдержанные клетки перечисляются отдельно. Дальнейшие ограничения конкретного прогона определяются только его журналами, а не заранее придуманными значениями Windows.

## Чтение исходников

- `DESIGN.md`: раздельные наблюдатели, SEH, seed-значения, стек, цепочка, политики и ограничения.
- `RAW_SCHEMA.md`: смысл записей и полей JSONL.
- `MAPPING.md`: только логическое соответствие указанным пользователем именам функций Wine.

Для сравнения между машинами сначала сравнивайте одинаковые ключи, номер доставки, относительные RIP/ExceptionAddress, флаги, значения и применимость полей. Абсолютные адреса, глубина стека и неопределённые/невыбранные поля нельзя автоматически трактовать как ошибку реализации.

## Проверка самой поставки

`VALIDATION.md` отделяет compile-only и синтетические проверки от не выполненного здесь нативного запуска Windows. `test_checker.py` позволяет повторить проверки Python-checker без Windows. Синтетические данные не являются эталоном Windows и в виде raw/summary не поставляются.
